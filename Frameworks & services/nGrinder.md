nGrinder는 네이버(NHN)가 만들어 공개한 오픈소스 부하 테스트(load test) 도구다. 실제 사용자가 몰리는 상황을 흉내내서, 시스템이 트래픽 규모에 얼마나 버티는지(TPS, 응답시간, 에러율)를 측정한다.

# 0. CI 테스트로는 왜 이걸 대신할 수 없는가
[[Grafana & Loki & Prometheus]] 노트에서 CI와 모니터링이 서로 다른 질문에 답한다고 했는데, nGrinder는 그중에서도 CI 테스트와 정확히 대비되는 축을 담당한다.

- *CI의 유닛/통합 테스트*가 확인하는 것: *"요청 1개가 들어왔을 때, 로직이 정확한가?"* — 예를 들어 OrderService.createOrder가 가격을 정확히 계산하는지, 재고가 부족하면 정확히 예외를 던지는지.
- *nGrinder의 부하 테스트*가 확인하는 것: *"요청 수백~수천 개가 동시에 몰렸을 때도, 정확성과 속도가 유지되는가?"*

이 둘은 완전히 다른 문제다. 결제 로직이 100% 정확하게 짜여있어도, *동시에 1000명이 결제를 시도하면* DB 커넥션 풀이 고갈되거나, 재고 차감 로직에서 동시성 문제(두 명이 동시에 마지막 재고 1개를 주문)가 터지거나, 서버 응답시간이 몇 초씩 늘어질 수 있다. 이런 문제는:

1. 유닛 테스트로는 절대 발견할 수 없다 — 유닛 테스트는 요청 1개를 순차적으로 검증할 뿐, "동시에 여러 개가 몰리는 상황" 자체를 만들지 않는다.
2. CI 파이프라인의 통합 테스트로도 잘 안 잡힌다 — 보통 CI 환경은 가벼운 임시 VM이라, 애초에 그 정도 규모의 동시 요청을 만들어볼 리소스/설정이 없다.
3. *오직 실제와 비슷한 규모의 트래픽을 실제로 만들어봐야만* 발견할 수 있다 — 이게 nGrinder 같은 부하 테스트 도구가 필요한 이유다.

즉 정리하면: CI는 "이 코드가 맞는 로직인가"를 검증하는 정확성(Correctness) 테스트이고, nGrinder는 "이 로직이 실제 트래픽 규모에서도 버티는가"를 검증하는 확장성/안정성(Scalability) 테스트다. *CI를 통과했다고 해서 프로덕션에서 트래픽에 무너지지 않는다는 보장은 전혀 되지 않는다* — 이 둘은 서로를 대체하지 못하고, 둘 다 필요하다.

# 1. 아키텍처 — Controller와 Agent
nGrinder는 두 종류의 컴포넌트로 구성된다.

- *Controller*: 웹 UI를 제공하는 중심 서버. 여기서 테스트 스크립트를 작성/관리하고, 테스트를 실행시키고, 여러 Agent로부터 결과를 모아서 집계/그래프로 보여준다.
- *Agent*: 실제로 부하(가짜 사용자, Virtual User)를 만들어서 대상 서버에 요청을 쏘는 주체. Controller가 "지금부터 초당 이만큼 요청을 보내라"고 지시하면, Agent가 실제로 그 요청들을 만들어서 발사한다.

Agent를 *여러 대* 띄워서 Controller가 동시에 관리하게 하면, 한 대의 컴퓨터가 만들 수 있는 부하보다 훨씬 큰 규모의 트래픽을 분산해서 만들어낼 수 있다 — 이게 nGrinder가 대규모 부하 테스트에 쓰이는 이유다(하나의 Agent 컴퓨터로는 물리적으로 만들 수 있는 동시 접속 수에 한계가 있으니까).

# 2. 테스트 스크립트 작성
실제 사용자의 행동 패턴을 스크립트로 짜야 의미 있는 테스트가 된다. nGrinder는 Groovy(또는 Jython) 기반으로 스크립트를 작성한다. 예를 들어 이 프로젝트라면:

```
로그인 요청 → 상품 목록 조회 → 장바구니 담기 → 주문 생성 → Toss 결제 승인
```
이런 하나의 흐름을 스크립트로 만들고, 이걸 *가상 사용자(Vuser) 수백~수천 명이 동시에 반복 실행*하도록 설정한다.

주요 설정값:
- *Vuser 수*: 동시에 시뮬레이션할 가상 사용자 수
- *테스트 지속시간*: 얼마나 오래 부하를 유지할지
- *Ramp-up*: 부하를 처음부터 최대치로 확 주는 게 아니라, 서서히 늘려가는 것 — 실제 트래픽도 갑자기 폭증하기보다 점진적으로 느는 경우가 많고, 서서히 늘리면서 "어느 지점에서 시스템이 무너지기 시작하는지"를 관찰할 수 있다.

# 3. 핵심 지표 읽는 법
테스트가 끝나면 nGrinder는 다음 지표들을 보여준다.

- *TPS(Transactions Per Second)*: 초당 처리한 요청(트랜잭션) 수. 이게 높을수록 시스템이 많은 트래픽을 처리하고 있다는 뜻이지만, 그냥 높다고 좋은 게 아니라 *응답시간/에러율과 같이 봐야* 의미가 있다.
- *평균/최대 응답시간*: 요청 하나가 처리되는 데 걸린 시간. Vuser를 늘려가면서 이 값이 급격히 늘어나기 시작하는 지점이 바로 시스템의 한계(bottleneck)다.
- *에러율*: 실패한 요청의 비율. 정상적으로는 0%에 가까워야 하고, Vuser가 늘면서 에러율이 갑자기 튀는 지점이 있다면 그게 시스템이 감당 못 하기 시작하는 경계선이다.

이 세 지표를 Vuser 수를 점점 늘려가며 그래프로 그려보면, "이 시스템은 동시 사용자 몇 명까지는 문제없이 버티고, 그 이상부터 응답이 느려지거나 에러가 나기 시작한다"는 *시스템의 실제 처리 용량(capacity)* 을 파악할 수 있다.

# 4. 언제 실행하는가
매 커밋마다 CI 파이프라인에 끼워 넣기엔 부담이 크다 — 부하 테스트는 몇 분~몇십 분씩 걸리고, Agent 자원도 따로 필요해서 매번 돌리기엔 비용이 크다. 그래서 보통은:

- 주요 릴리즈(큰 기능 배포) 직전에 한 번
- 정기적으로(예: 분기별) 용량 계획(capacity planning) 목적으로
- 특정 기능(할인 이벤트, 선착순 구매처럼 트래픽이 몰릴 게 예상되는 경우) 배포 전에

이런 시점에 별도로 실행하는 경우가 많다. (참고로 k6 같은 좀 더 코드 중심적이고 가벼운 도구는 CI 파이프라인에 매번 가볍게 끼워 넣는 경우도 있는데, nGrinder는 GUI 중심의 무거운 도구라 그렇게까지는 잘 안 쓴다 — [[Redis]] 노트에서 "k6/nGrinder"를 같이 언급했던 게 이런 성격 차이 때문이다.)

# 5. 이 프로젝트에 적용
[[Redis]] 노트에서 "성능 측정" 도구로 이미 한 번 언급된 도구다. 특히 이 프로젝트에서 부하 테스트가 의미 있는 지점은:

- *Toss 결제 흐름*: 동시에 여러 주문이 몰릴 때 결제 승인(authTossPayment)이 안정적으로 처리되는지
- *재고 차감 로직*(추후 CI/CD 이후 "상품 수량 로직" 단계에서 구현 예정): 동시에 여러 명이 같은 상품의 마지막 재고를 주문하려고 할 때, 재고가 실제로 정확히 하나만 차감되고 중복 판매가 안 일어나는지 — 이건 코드 리뷰만으로는 확신할 수 없고, 실제로 동시 요청을 만들어서 검증해야 하는 대표적인 케이스다.

지금 당장 급한 기능은 아니지만, 재고 처리 로직을 구현하는 단계에 다다르면 그 로직이 진짜로 동시성 문제 없이 안전한지 확인하는 용도로 nGrinder를 붙여보는 게 자연스러운 다음 단계다.
