Grafana/Loki/Prometheus는 "배포된 시스템이 지금 이 순간 살아서 잘 돌아가고 있는가"를 계속 지켜보기 위한 관측성(Observability) 스택이다. Prometheus는 숫자(메트릭)를 모으고, Loki는 로그를 모으고, Grafana는 이 둘을 하나의 대시보드에서 보여주는 시각화 도구다.

# 0. CI 테스트가 있는데 왜 이게 또 필요한가
결론부터 말하면, CI(빌드+테스트)와 모니터링은 *완전히 다른 시점, 다른 질문에 답하는 도구*다.

- *CI/CD가 답하는 질문*: "이 커밋을 배포해도 안전한가?" — 딱 그 순간, 깨끗한 임시 환경(Runner VM)에서 미리 짜둔 테스트 코드로 딱 한 번 검증하고 끝난다. 검증이 끝나면 그 환경 자체가 사라진다.
- *모니터링이 답하는 질문*: "지금 이 순간, 실제로 돌아가고 있는 서버가 잘 버티고 있는가?" — 배포가 끝난 뒤에도 서비스는 몇 시간, 며칠, 몇 달을 계속 운영된다. 그 기간 동안:
	  - 실제 사용자 트래픽이 예상보다 몰릴 수 있다
	  - 메모리 누수로 서버가 점점 느려질 수 있다(유닛 테스트는 이런 걸 절대 못 잡는다 — 테스트는 몇 초 안에 끝나니까)
	  - 특정 시간대에만 에러율이 튀는 패턴이 있을 수 있다
	  - DB 커넥션 풀이 고갈되거나, 디스크가 꽉 차거나, 외부 API(Toss 등)가 느려지는 등 *코드 로직과 무관한 인프라적 문제*가 생길 수 있다

이걸 CI 테스트가 절대 대신할 수 없는 이유는 간단하다 — *테스트는 "정해진 입력 → 정해진 출력이 맞는가"를 확인하는 것*이고, 모니터링은 *"예측 못 한 실제 상황에서 시스템이 어떻게 반응하고 있는가"를 계속 관찰하는 것*이라, 애초에 검증하는 대상 자체가 다르다.

정리하면:
1. CI/CD = 배포 *전* 게이트 (이 코드가 맞는 로직인가)
2. 모니터링(Grafana/Loki/Prometheus) = 배포 *후* 지속 관찰 (지금 살아있는 시스템이 건강한가)
3. 부하 테스트(nGrinder) = 배포 *전후* 간헐적 검증 (이 시스템이 실제 트래픽 규모를 버틸 수 있는가)

# 1. 메트릭(Metric) vs 로그(Log) — 서로 다른 두 종류의 관측 데이터
- *메트릭*: 숫자로 된 시계열 데이터. "지금 CPU 사용률이 몇 %인지", "1분 동안 요청이 몇 건 들어왔는지", "응답시간 평균이 얼마인지" 같은 것. *"얼마나/몇 번"* 질문에 답하고, 그래프로 추세를 보기에 최적화되어 있다.
- *로그*: 특정 시점에 무슨 일이 있었는지 서술하는 텍스트. "몇 시 몇 분에 어떤 사용자의 어떤 요청에서 어떤 예외가 터졌는지" 같은 것. *"무슨 일이 있었는지"* 질문에 답한다.

둘 다 필요한 이유: 메트릭으로 *"방금 에러율이 갑자기 튀었다"* 는 이상 징후를 먼저 알아채고(경보 역할), 그 시간대의 로그를 뒤져서 *"왜 그랬는지"* 구체적인 원인을 찾아낸다(수사 역할). 메트릭만 있으면 "뭔가 이상하다"까지만 알고, 로그만 있으면 방대한 텍스트 더미에서 언제/어디를 봐야 할지 모른다.

# 2. Prometheus — 메트릭 수집
## 2-1. Pull 방식
Prometheus의 핵심 동작 원리는 *Pull(끌어오기)* 방식이다 — 애플리케이션이 알아서 Prometheus한테 데이터를 밀어넣는(Push) 게 아니라, *Prometheus가 주기적으로(예: 15초마다) 애플리케이션의 특정 엔드포인트를 직접 찾아가서 메트릭을 긁어온다(scrape).*

이 방식의 장점: 애플리케이션 입장에서는 그냥 "현재 상태를 보여주는 엔드포인트 하나"만 열어두면 되고, 얼마나 자주/누가 가져가는지 신경 쓸 필요가 없다. Prometheus 서버가 죽어도 애플리케이션에는 영향이 없다(애플리케이션은 그냥 자기 할 일만 함).

## 2-2. Spring Boot에서는 어떻게 노출하는가
Spring Boot는 *Micrometer*라는 계측(instrumentation) 라이브러리를 통해, 별다른 코드 작성 없이도 자동으로 여러 메트릭(HTTP 요청 수/응답시간, JVM 힙 메모리, GC 횟수, DB 커넥션 풀 상태 등)을 수집한다. 여기에 spring-boot-starter-actuator + micrometer-registry-prometheus 의존성만 추가하면, /actuator/prometheus 라는 엔드포인트가 Prometheus가 이해하는 포맷으로 이 메트릭들을 그대로 노출해준다. Prometheus 설정 파일에 이 엔드포인트 주소만 등록해두면 자동으로 주기적으로 긁어간다.

## 2-3. 시계열로 저장한다는 것의 의미
Prometheus는 각 메트릭 값에 수집된 시각(timestamp)을 찍어서 저장한다. 그래서 "지금 값이 얼마인가"뿐 아니라 "지난 1시간 동안 어떻게 변해왔는가"를 그대로 조회할 수 있다 — 이게 그래프로 추세를 볼 수 있는 이유다.

# 3. Grafana — 시각화
Grafana 자체는 데이터를 수집하지 않는다. Prometheus, Loki 같은 *여러 데이터 소스에 쿼리를 날려서, 그 결과를 하나의 대시보드에 통합해서 보여주는 도구*다.

- *PromQL*: Prometheus에 쿼리하는 전용 문법. 예를 들어 rate(http_server_requests_seconds_count[5m])는 "최근 5분간 초당 요청 수 변화율"을 뜻한다.
- *패널/대시보드*: 이 쿼리 결과를 꺾은선 그래프, 게이지, 표 등으로 보여주는 화면 단위를 패널이라 하고, 여러 패널을 모아놓은 게 대시보드다.
- *Alerting*: 특정 조건(예: 5분간 에러율이 5%를 넘음)을 만족하면 Slack/이메일 등으로 알림을 보내는 기능도 Grafana 안에서 설정 가능하다 — 이게 있으면 대시보드를 계속 쳐다보고 있지 않아도, 문제가 생기면 먼저 알려준다.

# 4. Loki — 로그 수집
## 4-1. "로그계의 Prometheus"
Loki는 Grafana를 만든 회사(Grafana Labs)가 만든 로그 저장/조회 시스템이고, 설계 철학이 Prometheus와 닮아있다. 기존에 로그 수집에 널리 쓰이던 *Elasticsearch(ELK 스택)와 비교하면 이해가 빠르다.*

- *Elasticsearch*: 로그의 *모든 단어를 색인(full-text indexing)* 한다. 그래서 로그 본문 안의 어떤 단어로든 빠르게 검색할 수 있지만, 그만큼 색인을 만드는 데 계산 자원과 저장 공간을 많이 먹는다.
- *Loki*: 로그 본문 전체를 색인하지 않는다. 대신 *컨테이너 이름, 로그 레벨 같은 라벨(메타데이터)만 색인*하고, 실제 로그 본문은 그냥 압축해서 저렴한 스토리지(S3 등)에 통째로 저장해둔다. 그래서 훨씬 가볍고 운영 비용이 낮다 — 대신 본문 전체를 대상으로 한 임의 검색은 Elasticsearch보다 느릴 수 있다는 트레이드오프가 있다.

이건 [[Redis]] 노트에서 다룬 "일관성을 조금 포기하고 성능/비용을 챙긴다"는 트레이드오프 사고방식, [[Docker]] 노트의 "컨테이너는 VM보다 기능은 적지만 훨씬 가볍다"는 논리와 같은 결의 선택이다 — *"완벽하게 다 되는 것"보다 "이 프로젝트 규모에 필요한 만큼만, 훨씬 싸고 가볍게"* 를 택하는 것.

## 4-2. 로그를 어떻게 Loki로 보내는가
서버/컨테이너에 떠있는 로그 파일이나 docker logs로 나오는 출력을 Loki로 실제로 실어 나르는 별도의 *수집 에이전트*가 필요하다(Promtail, 또는 최근엔 이를 통합한 Grafana Alloy). 이 에이전트가 각 컨테이너의 로그를 계속 tail(꼬리 읽기)하면서 Loki로 전송한다.

## 4-3. LogQL
Loki에 쿼리하는 문법도 PromQL과 닮아있다. 예를 들어 {container="mall-backend"} |= "ERROR"는 "mall-backend 컨테이너의 로그 중 ERROR라는 문자열이 포함된 것"을 뜻한다. 라벨({container="..."})로 먼저 좁히고, 그 안에서 텍스트 필터(|= "...")를 추가하는 구조다.

# 5. 셋이 합쳐진 실제 흐름
```
[Spring Boot 앱] --(/actuator/prometheus 노출)--> [Prometheus가 주기적으로 긁어감]
[Docker 컨테이너 로그] --(Promtail이 tail)--> [Loki로 전송]

[Grafana] --(PromQL로 Prometheus에 쿼리)--> 메트릭 그래프
[Grafana] --(LogQL로 Loki에 쿼리)--> 로그 조회
```
운영자는 결국 *Grafana 화면 하나만 열어두면*, 메트릭 그래프에서 이상 징후를 발견하고 → 같은 화면에서 그 시간대 로그로 바로 넘어가서 원인을 찾는 흐름을 만들 수 있다.

# 6. 이 프로젝트에 적용
로드맵상 CI/CD 다음 단계로 이미 예정된 부분이다("CI/CD + Web Server → Grafana/Prometheus + Mock Data"). 실제로 도입할 때 순서:

1. backend/shopping-mall-api에 spring-boot-starter-actuator + micrometer-registry-prometheus 의존성 추가
2. application.yml에서 /actuator/prometheus 엔드포인트 노출 설정
3. docker-compose.yml에 prometheus, grafana, loki, promtail 서비스 추가([[Docker]] 노트에서 다룬 것과 같은 방식으로 서비스 블록 하나씩 늘어나는 것뿐이다)
4. Prometheus 설정 파일에 백엔드의 /actuator/prometheus 주소 등록(scrape target)
5. Grafana에서 Prometheus/Loki를 데이터 소스로 등록하고 대시보드 구성

MySQL/Redis도 각각 전용 익스포터(mysqld_exporter, redis_exporter)를 붙이면 DB/캐시 자체의 상태(커넥션 수, 캐시 히트율 등)까지 같은 방식으로 Prometheus에 노출시켜 모니터링할 수 있다 — 지금 당장은 애플리케이션 메트릭부터 시작하고, 나중에 확장하면 된다.
