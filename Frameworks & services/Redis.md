Redis(REmote DIctionary Server)는 디스크가 아닌 RAM에 데이터를 저장하고 처리하는 인메모리 key-value 저장소다. RDBMS처럼 테이블/스키마를 강제하지 않는 NoSQL 계열이고, 이 프로젝트에서는 JWT refresh token 저장용으로 쓰고 있다.

# 0. Redis가 왜 빠른가 (원리)
이걸 이해하려면 컴퓨터 구조에서 배우는 메모리 계층(memory hierarchy) 개념을 그대로 가져오면 된다 — CPU에 가까울수록(레지스터 > 캐시(L1/L2/L3) > RAM > SSD > HDD) 빠르지만 용량이 작고, 멀어질수록 느리지만 용량이 크다. MySQL 같은 RDBMS는 결국 디스크(SSD/HDD)에 데이터를 저장하고, 디스크 I/O는 RAM 접근보다 자릿수 자체가 다르게 느리다(대략 RAM 접근이 나노초 단위라면 디스크 I/O는 마이크로초~밀리초 단위 — 수천~수백만 배 차이). Redis는 이 디스크 I/O 자체를 없애고 RAM 접근만으로 응답하기 때문에 빠르다. 캐싱의 본질은 결국 이거다: *더 느린 저장소로 가는 요청 자체를 없애는 것.*

여기에 하나가 더 있다 — Redis는 기본적으로 *싱글 스레드*로 명령어를 처리한다. 언뜻 "스레드를 여러 개 써야 빠른 거 아닌가" 싶을 수 있는데, 오히려 그 반대의 이유로 빠르다.

- 멀티스레드 방식은 여러 스레드가 같은 데이터에 동시에 접근하지 못하게 락(lock)을 걸어야 하고, 그 락을 얻고 기다리는 데 드는 오버헤드(컨텍스트 스위칭, 락 경합)가 상당하다.
- Redis는 애초에 한 번에 하나의 명령어만 처리하므로 락이 필요 없다 — 그래서 모든 단일 명령어(예: INCR)가 원자적(atomic)으로 보장된다. 여러 클라이언트가 동시에 요청을 보내도 Redis 내부에서는 한 줄로 순서대로 처리되기 때문에 "동시에 두 클라이언트가 같은 값을 읽고 쓰다가 하나의 갱신이 유실되는" 경쟁 상태(race condition)가 원천적으로 생기지 않는다.
- 그럼 "동시에 여러 클라이언트의 연결은 어떻게 처리하냐"는 의문이 남는데, 이건 스레드를 늘리는 대신 *I/O 멀티플렉싱*(리눅스의 epoll 같은 커널 기능)으로 해결한다 — 수많은 소켓 연결의 상태를 하나의 이벤트 루프가 감시하다가, 실제로 읽을 데이터가 준비된 소켓만 골라서 순서대로 처리한다. 스레드를 여러 개 만드는 대신, 하나의 스레드가 "누가 준비됐는지"를 효율적으로 감시하는 방식이다.

정리하면: (1) 디스크 I/O를 없애고 RAM만 쓰는 것, (2) 락이 필요 없는 싱글 스레드 처리 + I/O 멀티플렉싱, 이 두 가지가 Redis가 빠른 근본 원리다.

# 1. 실무 사용 목적
- 캐싱: 위 0번 원리대로, 디스크(DB)까지 안 가고 RAM에서 바로 응답해서 조회 속도를 높인다.
- TTL(Time To Live): 네트워크 패킷의 TTL과 이름은 같지만 의미는 조금 다르다 — 여기서는 "이 데이터가 RAM에 살아있을 수 있는 시간"을 뜻한다. 뒤에서 다룰 캐시 일관성 문제를 완화하는 핵심 도구.
- 세션/토큰 저장소: 이 프로젝트에서 실제로 쓰는 용도 — JWT의 refresh token을 저장해서 로그아웃 시 즉시 무효화하거나, 재발급 시점에 대조하는 용도로 쓴다.
- 성능 측정: k6/nGrinder 같은 부하 테스트 도구로 Redis 적용 전후 응답속도를 비교 측정할 수 있다.

더 많은 기능(Pub/Sub, 분산 락, 스트림 등)이 있지만, 지금은 캐싱/토큰 저장 목적으로만 쓰고 있어서 그 범위로 정리하고, 다른 목적이 필요해지면 이어서 추가한다.

# 2. 설치와 기본 명령어
mysql처럼 Homebrew로 설치하고 실행한다.

```bash
brew install redis
brew services start redis   # 백그라운드 서비스로 상시 실행
redis-cli                    # 대화형 클라이언트로 직접 명령어 입력
```

#### 생성/조회/삭제 (String 타입 기준)
```
set key value                  // key-value 형태로 저장
set key value ex 60             // ex로 초 단위 TTL 설정
get key                         // 값 조회, 없으면 nil
del key                         // 삭제, 성공 시 1, 대상 없으면 0
flushall                        // 모든 데이터 삭제 (개발 중 초기화할 때만, 운영에서 절대 쓰면 안 됨)
```

#### TTL 확인
```
ttl key
```
반환값으로 상태 판단:
- ttl >= 0: 남은 만료 시간(초)
- ttl = -2: TTL이 끝나서 이미 삭제된(존재하지 않는) key
- ttl = -1: TTL이 아예 설정 안 된, 영구 보존 key

#### key 조회
```
keys *          // 모든 key 조회 (운영 환경에서는 전체 스캔이라 위험 — 아래 4번 참고)
scan 0          // keys * 대신 실무에서 쓰는 안전한 방식
```

# 3. 데이터 타입 — String만 있는 게 아니다
지금까지는 String(단순 값 하나) 타입만 다뤘는데, Redis는 용도에 따라 여러 자료구조를 기본 타입으로 제공한다. 이게 사실 Redis를 "그냥 빠른 key-value 저장소"를 넘어서게 만드는 부분이고, 각 타입은 자료구조 수업에서 배운 개념과 그대로 대응된다.

| 타입 | 자료구조 | 실무 용도 예시 |
|---|---|---|
| String | 단순 값 | 캐시된 값 하나, 카운터(increment) |
| List | 연결 리스트 | 최근 조회 목록, 간단한 큐(FIFO) |
| Hash | 해시맵 | 객체 하나를 필드 단위로 저장(예: user:1의 name/email을 필드별로) |
| Set | 해시셋 | 중복 없는 태그, 팔로워 목록, 교집합/합집합 연산 |
| Sorted Set(ZSet) | 스킵 리스트(Skip List) + 해시맵 | 랭킹, 우선순위 큐(점수 기준 정렬 조회가 빠름) |

```
lpush recent:user1 productA          // List: 왼쪽에 삽입
hset user:1 name "홍길동" email "a@b.com"   // Hash: 필드 단위 저장/조회
sadd tags:productA "신선식품" "인기"          // Set: 중복 없이 추가
zadd ranking 100 "productA"           // ZSet: 점수(100)와 함께 추가
zrange ranking 0 -1 withscores        // ZSet: 점수 순 정렬 조회
```

Sorted Set이 특히 흥미로운데, 내부적으로 스킵 리스트를 쓰기 때문에 삽입/삭제/범위조회가 전부 O(log N)으로 보장된다 — "실시간 랭킹" 같은 기능을 RDBMS의 ORDER BY 쿼리 없이도 빠르게 구현할 수 있는 이유다.

# 4. key 네이밍 컨벤션
정형화된 RDBMS 테이블과 다르게, Redis는 비정형 key-value라서 key 자체의 이름으로 데이터의 의미와 구조를 표현해야 한다. 콜론(:)으로 구분하는 게 사실상의 표준이다.

```
users table의 name 컬럼 → key: users:[PK]:name 형태로 매핑
```

장점:
1. 가독성: key만 보고도 무슨 데이터인지 파악 가능
2. 일관성: 유지보수가 쉬워짐
3. 검색/필터 용이성: 패턴 매칭(예: users:1:*)으로 특정 유형의 key를 쉽게 찾을 수 있음
4. 확장성: 다른 key와의 이름 충돌을 줄임

한 가지 실무 주의사항: keys * 나 keys users:* 처럼 패턴 매칭 조회는 Redis가 전체 keyspace를 훑는 O(N) 연산이라, 데이터가 많아지면 그 순간 Redis 전체가 멈추는 것처럼 느려질 수 있다(싱글 스레드이므로 이 훑는 동안 다른 요청을 전혀 처리 못 함). 그래서 운영 환경에서는 keys 대신 scan(커서 기반으로 조금씩 나눠서 순회, 다른 명령어 처리를 막지 않음)을 쓰는 게 정석이다.

# 5. 캐시 사용 패턴 — Cache-Aside + Write-Around
실무에서 가장 널리 쓰이는 조합이고, 이 프로젝트에서도 이 방식을 기준으로 설계했다.

- *Cache-Aside(Look-Aside) 패턴*: 조회 요청이 오면 DB가 아니라 Redis(캐시)를 먼저 찾는다.
  1. 애플리케이션이 CRUD 요청을 받으면 DB가 아닌 Redis에서 먼저 탐색
  2. cache hit이면 즉시 반환 (DB에 요청 안 감)
  3. cache miss면 DB에서 조회한 뒤 그 결과를 Redis에 저장
- *Write-Around 패턴*: 생성/수정/삭제(CUD) 작업은 Redis를 거치지 않고 DB에만 직접 반영한다.

이 두 패턴을 같이 쓰면 생기는 문제: CUD는 DB에만 반영되므로, 이미 캐시에 올라가 있던 옛날 값과 DB의 새 값 사이에 *일관성이 깨진다*(캐시는 옛날 값을 그대로 들고 있음).

그런데도 실무에서 이 조합을 자주 쓰는 이유:
- 일관성과 성능은 트레이드오프 관계다 — 한쪽을 얻으면 다른 쪽을 어느정도 포기해야 한다. Redis를 쓰는 목적 자체가 성능이므로, 일관성을 다소 포기하더라도 성능 이득을 우선한다.
- TTL로 이 단점을 완화할 수 있다 — TTL이 지나면 캐시가 자동으로 사라지므로(cache miss 유도), 다음 조회 때 DB의 최신 값으로 다시 채워진다. (단, TTL이 아직 안 끝난 시점에 수정이 일어나면 그 사이엔 여전히 일관성이 깨진 채로 남아있다 — TTL은 "훼손을 최소화"하는 것이지 "완전히 보장"하는 게 아니다.)

그래서 Redis 캐싱은 다음 조건의 데이터에 적합하다:
- 자주 조회되는 데이터: 읽기가 잦을수록 캐싱 이득이 큼
- 잘 안 변하는 데이터: 일관성 훼손 가능성 자체가 낮음
- 실시간 정확도가 크게 중요하지 않은 데이터: 훼손되어도 손해가 적음

즉 TTL은 두 가지 목적을 동시에 수행한다: (1) 일관성 훼손을 최소화하고, (2) 오랫동안 안 쓰이는(우선순위 낮은) 데이터를 메모리에서 자동으로 정리한다.

# 6. TTL은 실제로 어떻게 지워지는가 (만료 원리)
TTL이 끝났다고 그 순간 즉시 메모리에서 사라지는 건 아니다. Redis는 두 가지 방식을 같이 쓴다.

- *Lazy(수동적) 만료*: 어떤 key에 접근(get 등)했을 때, 그 key의 TTL이 지났으면 그제서야 삭제하고 nil을 반환한다. 접근 안 하면 만료됐어도 당장은 메모리에 남아있을 수 있다.
- *Active(능동적) 만료*: 백그라운드에서 주기적으로(기본 초당 10회) TTL이 설정된 key 중 일부를 무작위로 샘플링해서, 만료된 게 일정 비율 이상이면 그만큼 삭제하고 이 과정을 반복한다.

이렇게 두 가지를 같이 쓰는 이유는 절충이다 — 모든 key의 만료를 매 순간 정확히 검사하면 그 자체가 부담(싱글 스레드에서 이 검사에 시간을 뺏기면 다른 요청 처리가 밀림)이고, 반대로 접근할 때만 검사하면(Lazy만 쓰면) 아무도 안 읽는 key가 영원히 메모리를 차지할 수 있다. 그래서 "접근 시 확인 + 주기적으로 일부만 확인"을 같이 써서 균형을 맞춘다.

# 7. 메모리 관리와 Eviction 정책
RAM은 디스크보다 훨씬 비싸고 용량이 작다 — 그래서 Redis는 maxmemory 설정으로 쓸 수 있는 메모리 상한을 두고, 그 한도를 넘으면 무엇을 지울지 정하는 *eviction(축출) 정책*을 둔다.

| 정책 | 동작 |
|---|---|
| noeviction | 새 데이터 저장을 거부(에러 반환), 아무것도 안 지움 |
| allkeys-lru | 전체 key 중 가장 오래 안 쓰인 것부터 삭제 (LRU) |
| volatile-lru | TTL이 설정된 key 중에서만 LRU로 삭제 |
| allkeys-lfu | 전체 key 중 사용 빈도가 가장 낮은 것부터 삭제 (LFU) |
| volatile-ttl | TTL이 얼마 안 남은 key부터 우선 삭제 |

LRU(Least Recently Used)와 LFU(Least Frequently Used)는 자료구조/운영체제 수업에서 페이지 교체 알고리즘으로 배우는 것과 완전히 같은 개념이다 — OS가 물리 메모리(페이지 프레임)가 가득 찼을 때 어떤 페이지를 디스크로 내쫓을지 정하는 문제와, Redis가 RAM이 가득 찼을 때 어떤 key를 지울지 정하는 문제는 본질적으로 동일한 문제(제한된 캐시 공간에서 무엇을 유지할지 결정)다. LRU는 보통 "사용 순서를 기록한 연결리스트 + 해시맵" 조합으로 구현하는 것도 그대로 대응된다.

# 8. 영속성(Persistence) — 인메모리인데 왜 재시작해도 데이터가 남을 수 있는가
RAM은 전원이 꺼지면 내용이 사라지는 휘발성 저장장치다. 그런데 Redis 서버를 재시작해도 데이터가 그대로 남아있는 경우가 있는데, 이건 Redis가 디스크에 백업을 남겨두기 때문이다. 두 가지 방식이 있다.

- *RDB(Redis Database) 스냅샷*: 특정 시점의 전체 메모리 상태를 통째로 디스크 파일로 저장. 빠르고 파일이 작지만, 마지막 스냅샷 이후의 변경분은 유실된다.
- *AOF(Append Only File)*: 모든 쓰기 명령어를 순서대로 로그 파일에 계속 append. 재시작 시 이 로그를 처음부터 다시 실행해서 상태를 복원한다. 데이터 유실 위험이 훨씬 적지만 파일이 커지고 복구 속도가 느리다.

AOF 방식은 사실 RDBMS에서 배우는 WAL(Write-Ahead Log, 커밋 전에 로그부터 기록해서 장애 시 복구하는 방식)과 개념적으로 완전히 같다 — "실제 자료구조를 바로 영구저장소에 반영하기보다, 무슨 작업을 했는지 순서대로 기록해두고 그걸 재생(replay)해서 상태를 복원한다"는 발상이 동일하다.

지금 이 프로젝트는 refresh token 저장 용도로만 쓰고 있어서, 영속성을 켜지 않아도 큰 문제는 없다(Redis가 재시작되면 로그인된 사용자들이 재로그인해야 하는 정도의 영향) — 다만 이 트레이드오프는 구성 시점에 의식적으로 결정해야 하는 부분이라 알아두는 게 좋다.

# 9. 복제(Replication)와 확장 (기초)
- *Master-Replica 복제*: Master 서버 하나와 Replica(복제본) 서버 여러 대를 둔다. Replica는 처음 붙을 때 Master의 RDB 스냅샷을 통째로 받아온 뒤(초기 동기화), 그 이후로는 Master가 받는 쓰기 명령어를 실시간으로 전달받아 그대로 적용한다(명령어 전파, 8번의 AOF와 비슷한 발상 — "명령어 자체를 복제"). CUD는 Master에만, 조회는 Replica들에 분산해서 부하를 나눌 수 있다.
- *Redis Sentinel*: Master가 죽었을 때 Replica 중 하나를 자동으로 새 Master로 승격시켜주는 장애 감지/자동 failover 도구.
- *Redis Cluster*: 데이터를 여러 노드에 샤딩(분산)해서, 하나의 Redis로는 감당 못 할 규모의 데이터/트래픽을 처리하는 방식. [[Kubernetes]] 노트에서 다룬 "언제 단일 서버를 넘어서야 하는가"와 같은 맥락 — 지금 프로젝트 규모에서는 필요 없다.

# 10. Spring Boot에서 Redis 연동하기
```yaml
# application.yml
spring:
  data:
    redis:
      host: localhost
      port: 6379
```

연동 방식은 크게 두 가지다.

- *RedisTemplate / StringRedisTemplate*: Redis 명령어를 직접 다루는 저수준 API. 이 프로젝트의 RefreshTokenRepository가 이 방식이다 — save/find/delete를 직접 구현해서 명시적으로 key 구조와 TTL을 제어한다.
- *Spring Cache 추상화(@Cacheable, @CacheEvict)*: 메서드 단위로 "이 메서드의 반환값을 캐싱해라"를 어노테이션으로 선언만 하면 되는 더 간편한 방식. 예를 들어 상품 조회 메서드에 @Cacheable("products")를 붙이면, 같은 파라미터로 다시 호출될 때 메서드 실행 자체를 건너뛰고 캐시된 값을 반환한다. 지금 이 프로젝트는 상품(Product) 캐싱을 아직 안 쓰고 있는데(수량 정합성 문제 때문에 write-around만으로는 위험하다고 판단해서 보류한 상태, 아래 11번 참고), 나중에 도입한다면 이 방식이 refresh token처럼 직접 구현하는 것보다 훨씬 적은 코드로 가능하다.

# 11. DB 성능 튜닝 — Redis는 여러 방법 중 하나일 뿐
Redis는 캐싱으로 DB 조회 성능을 높이는 방법인데, DB 성능을 높이는 방법이 캐싱만 있는 건 아니다.

1. SQL 튜닝
2. 캐싱 서버 활용(Redis)
3. 레플리케이션(master-slave)
4. 샤딩
5. DB 스케일업(수직 확장)

- 2번(Redis)은 DB와 서버 사이에 캐시를 둬서 조회 성능을 높이고 DB 트래픽을 낮추는 방식이다.
- 3번은 Primary 서버 한 대 + Replica 서버 여러 대로 master-slave 관계를 구축해서, CUD는 Primary에, 조회는 Replica에 분산하는 수평적 확장이다. 조회 요청이 전체 트래픽의 압도적 다수(보통 80% 이상)를 차지하는 경우가 많아서, 조회 전용 서버를 따로 두는 게 효과적이다.
- 4번은 큰 데이터베이스의 데이터를 샤드 키(보통 PK)라는 기준으로 여러 데이터베이스에 나눠 분산하는 방식이다. 요청이 쿼리의 PK에 따라 서로 다른 DB 서버로 향하게 해서 트래픽을 여러 방향으로 분산시키는 수평적 확장이다.
- 5번은 CPU/SSD 등 하드웨어 자체를 업그레이드하는 수직적 확장이다.

이 5가지 중 가장 먼저 진행해야 하는 건 SQL 튜닝이다 — 캐싱이나 복제/샤딩 같은 인프라적 해법을 붙이기 전에, 애초에 비효율적인 쿼리/인덱스부터 고치는 게 비용 대비 효과가 가장 크기 때문이다.

# 12. 이 프로젝트에서의 현재 사용 현황
- 지금은 JWT refresh token 저장/조회/대조 용도로만 Redis를 쓰고 있다(RefreshTokenRepository).
- Product 데이터를 Redis에 올려서 조회 성능을 높이는 것도 초기에 고려했으나, 수량(재고) 정보처럼 정합성이 민감한 데이터는 Cache-Aside + Write-Around 조합의 일관성 훼손 위험(5번)이 기능에 지장을 줄 수 있다고 판단해서 보류하고, 대신 조회만 하는 안정적인 데이터부터 캐싱하는 방향으로 다시 설계하기로 한 상태다.
- docker-compose.yml에는 아직 redis 서비스가 명시적으로 추가되지 않았고, 현재는 로컬에 Homebrew로 띄운 Redis가 우연히 실행 중이라 동작하는 상태다 — [[Docker]] 노트의 Compose 예시에 있는 redis 서비스 블록을 실제로 추가하면 이 부분이 해결된다.
