Redis는 인메모리 dbms로 디스크가 아닌 ram에 데이터를 저장하고, 처리하는 NoSQL 데이터 저장소이다.

# 0. 실무 사용
- 캐싱 : 디스크에서 정보를 읽어와 ram에 저장하므로서 빠른 조회가 가능하도록 한다.
- TTL(Time To Live) : 네트워크의 ttl과 동일한 기능으로, 데이터가 ram에 저장되는 시간을 설정할 수 있다.
- 성능 측정 : k6 / n68m과 같은 데스트 도구를 통해 redis의 성능 측정 가능

더 많은 기능들이 존재하지만, 현재 캐싱의 목적으로 redis를 공부하기 때문에, 추후에 다른 목적 및 기능 추가가 요구되는 경우, 살점을 붙여서 메모

# 1. redis 사용 명령어
- mysql처럼 homebrew를 통해 설치를 진행하고, *brew services start redis* 명령어를 통해 redis 실행
- 이후 redis-cli를 통해 직접 제어 가능

#### 생성
```
set [key] [value] //key-value형식의 비정형 데이터를 저장
set [key] [value] ex [second] // ex를 통해 second만큼의 ttl설정
```

#### 조회
```
get [key] // return value
```

#### 삭제
```
del [key] // return이 1인 경우 삭제 성공, nil인 경우 삭제 데이터 식별 x
flushall // 모든 데이터 삭제
```
#### TTL 조회
- 앞선 설명대로 TTL을 데이터에 적용가능하고, 이는 명령어를 통해 확인 가능
```
ttl [key] // 해당 데이터의 ttl확인
```
- 이때 return 값에 따라 데이터의 상태 확인 가능
	- ttl >= 0 : 남은 ttl 시간 확인
	- ttl = -2 : 설정된 ttl 시간이 끝나 사라진 데이터
	- ttl = -1 : ttl이 설정되지 않은 데이터(삭제되지 않았음)

#### key 조회
```
key * // 모든 key 조회
```

# 2. key 네이밍 컨벤션
- 정형화된 데이터와 다르게 비정형 데이터는 key를 통해 모든 데이터를 구분지어야 하므로, key의 네이밍 패턴을 통해 구분짓고, 식별할 수 있도록 설정
- 결론적으로는 콜론(:)을 통해 정형 데이터를 비정형 데이터로 매핑
```
users table에 존재하는 name의 경우 users:[PK]:name과 같은 방식으로 key설정
```

#### 장점
1. 가독성 : 데이터의 의미와 용도 파악
2. 일관성 : 유지보수가 쉬워짐
3. 검색 및 필터성 용이 : 패턴 규칙을 통한 패턴 매핑으로 특정 유형의 key를 쉽게 찾을 수 있음
4. 확장성 : 다른 key와의 중복을 줄임

# 3. redis 사용 패턴
- Look-Aside(Cache-Aside) 패턴 : 실무에서 권장하는 redis 사용 방식 패턴으로 다음과 같은 흐름을 갖는다.
	1. 어플리케이션의 crud 요청을 받게 되면 db가 아닌 redis(캐시)에서 우선 탐색을 한다.
	2. cache hit시 즉시 반환하여 db에 요청이 가지 않는다.
	3. cache miss일 경우, db에 접근 및 조회를 통해 redis에 저장을 한다.
- Write around 패턴 : CUD작업을 redis가 아닌 db에 접근하여 사용한다.
-> 위 두 패턴을 동시 사용하게 될 경우, 조회 작업은 redis를 통해(cache miss인 경우는 db도 같이), 생성/수정/삭제 작업은 db를 통해서만 이뤄지는데, 이때 데이터의 생성/수정/삭제의 경우 db에만 적용이 되기 때문에 redis 데이터와의 일관성이 유지되지 않음

다음과 같은 이유로 위 두 패턴을 실무에서 자주 사용함
- 데이터의 일관성을 다소 포기하고, 성능을 챙김 : 일관성과 성능은 반비례 관계이기 때문에, 한쪽을 얻으면 다른 한쪽을 잃는 수밖에 없고, redis의 사용목적인 성능을 더 중요하게 생각하여 일관성을 다소 포기하더라도 성능을 챙김
- 위 두 패턴을 동시에 사용하더라도 redis의 기능을 통해 단점을 최소화할 수 있음 : redis의 ttl을 설정하여 cache miss를 유도하고, 이를 통해 데이터를 db에서 일정시간마다 가져오게 하여 조회를 하게 함. (하지만 ttl이 만료되지 않은 시점에서 수정 -> 조회가 발생한 경우, 일관성이 유지되지 않는 것은 동일함.)

따라서 ttl을 적용하더라도 일관성 훼손을 최소화하는 것일뿐, 일관성이 완벽하게 보장되지는 않기 때문에 다음과 같은 조건의 데이터를 redis에 캐싱하는 것을 추천함.
- 자주 조회되는 데이터 : 잦은 읽기가 발생하는 경우, 높은 성능을 보임
- 잘 변하지 않는 데이터 : 최대한 일관성을 유지할 수 있음
- 실시간으로 정확하지 않아도 되는 데이터 : 일관성이 훼손되더라도 손해를 최소화할 수 있음

따라서 TTL은 두 가지의 목적으로 사용됨
- 데이터의 일관성 유지를 최대화함
- 자주 조회되지 않은 데이터(우선순위가 비교적 낮은 데이터)를 캐시메모리에서 삭제

-> Cache-aside + Write-around 패턴을 적용시 TTL을 사용

# 4. DB 성능 튜닝
- redis는 db조회 성능을 높이기 위해 캐싱을 사용하여 목적을 달성한다.
- 하지만 db조회 성능을 높이는 방식은 캐싱만 존재하는 것은 아니다.

#### db 성능 튜닝
1. SQL 튜닝
2. 캐싱 서버 활용(redis)
3. 레플리케이션 (master-slave)
4. 샤딩
5. DB 스케일업(수직 확장)

- 2번은 현재 배우는 redis를 db와 server사이에 두어, 조회성능을 높이고, db의 트래픽을 낮추는 방식이다.
- 3번은 primary 서버 한 대와 replica 서버 여러 대를 두어, CUD작업은 primary에, 조회 작업은 replica 서버를 통해 작업할 수 있도록 master - slave관계를 구축하는 것을 의미한다. 이는 조회 요청이 전체 요청의 80%의 압도적으로 많은 비중을 담당하기에 조회 전용 서버와 데이터 수정 작업 전용 서버를 나누어 놓는 수평적 확장을 의미한다.
- 4번은 큰 데이터베이스 내 데이터들을 *샤드 키* 라는 특별한 기준으로 데이터를 분류하여(보통 PK를 샤드 키로 설정), 여러 데이터 베이스로 나눠 관리하는 방식이다. 하나의 데이터베이스로 향하는 요청들이 조회 쿼리의 PK에 따라 요청이 향하는 데이터베이스 서버를 다르게 하여 트래픽을 여러 방향으로 분산시키는 수평적 확장을 의미한다.
- 5번은 cpu, SSD 등을 업그레이드하여 하드웨어적 성능을 높이는 방식을 의미한다.

위 5가지의 방법 중 가장 좋고, 먼저 진행해야 하는 방식은 sql튜닝이다.
