# 무결성 제약조건

## 개념

### 데이터 무결성

#### 정의
- 데이터베이스에 저장된 데이터의 일관성과 정확성을 지키는 것이다 — [[DB]]
- DBMS를 쓰는 장점 중 하나가 "데이터 무결성 유지"다 — [[DB]]

### 키

#### 슈퍼키와 후보키
- 슈퍼키: 튜플을 유일하게 식별할 수 있는 속성 또는 속성의 집합 — [[DB]]
- 후보키: 슈퍼키 중 **최소성**을 만족하는 것. 속성을 하나라도 빼면 유일성이 깨진다 — [[DB]]
- 예: `학번`이 유일하다면 (학번), (학번, 이름)은 모두 슈퍼키지만, 후보키는 (학번)뿐이다. (학번, 이름)은 이름을 빼도 여전히 유일하므로 최소가 아니다 (보충)

#### 기본키, 대체키, 대리키
- 기본키: 후보키 중 대표로 고른 키. NULL이 될 수 없고, 값이 잘 변하지 않아야 한다 — [[DB]]
- 대체키: 기본키로 뽑히지 않은 나머지 후보키 — [[DB]]
- 대리키: 마땅한 기본키가 없을 때 일련번호처럼 인공적으로 만드는 키 — [[DB]]
- 실전: ShoppingMall은 엔티티 id를 Long(MySQL BIGINT와 1:1 대응)으로 통일했다. 자동 증가 id는 대표적인 대리키다 — [[ShoppingMall - 트러블 슈팅 기록]] 2026-07-29 주차 "Data type"

#### 외래키
- 다른 릴레이션의 기본키를 참조해서 릴레이션 간의 관계를 표현한다. NULL과 중복을 허용한다 — [[DB]]

### 세 가지 무결성 제약조건

#### 도메인 무결성
- 튜플의 각 속성 값은 그 속성의 도메인에 정해진 값만 가져야 한다 — [[DB]]

#### 개체 무결성
- 기본키는 NULL일 수 없고 유일해야 한다. 삽입·수정할 때마다 검사한다 — [[DB]]

#### 참조 무결성
- 외래키 값은 참조하는 릴레이션에 기본키로 존재하는 값이거나 NULL이어야 한다 — [[DB]]
- 부모 튜플을 지울 때 고를 수 있는 동작은 네 가지다 — [[DB]] (SQL 키워드 표기는 보충)
    - `RESTRICT`: 삭제를 거부한다
    - `CASCADE`: 자식 튜플도 함께 지운다
    - `SET DEFAULT`: 외래키를 기본값으로 바꾼다
    - `SET NULL`: 외래키를 NULL로 바꾼다

## 실전: 애플리케이션에서의 무결성

### JPA 설정과 DB 제약의 관계

#### @Column(nullable = false)
- 테이블을 만들 때 NOT NULL 제약이 걸리도록 설정한다 — [[ShoppingMall - 트러블 슈팅 기록]] 2026-07-29 주차 "NPE"
- (보충) 이 설정은 DDL을 만들 때 쓰이는 것이고, 자바 코드에 null이 들어오는 것 자체를 막아주지는 않는다. 그래서 DTO를 엔티티로 바꿀 때 검증이 따로 필요했다

#### JPA의 cascade와 DB의 CASCADE는 다르다
- ShoppingMall은 cart–cartItem 관계에 cascade와 orphanRemoval을 설정했다 — [[ShoppingMall - 트러블 슈팅 기록]] 2026-07-29 주차 "단방향 / 양방향 매핑 엔티티"
- (보충) JPA의 cascade는 영속성 컨텍스트, 즉 자바 객체 수준에서 전이된다. 수업에서 배운 CASCADE는 DB가 외래키 제약에 따라 직접 수행한다. 결과는 비슷해 보여도 실행하는 주체가 다르다

### 입력값 검증

#### 공통 검증 로직 (CheckConfig)
- 문자열은 null과 blank를, 수량은 null과 음수를 검사하는 코드가 여기저기 겹쳐서 CheckConfig로 모았다 — [[ShoppingMall - 트러블 슈팅 기록]] 2026-07-29, 2026-08-05 주차
- 도메인 무결성을 DB에 닿기 전에 애플리케이션에서 먼저 지키는 역할이다 (보충: Bean Validation의 `@NotBlank`, `@Min` 같은 표준 방식도 있다)
