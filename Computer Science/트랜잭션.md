# 트랜잭션

## 개념

### 정의

#### 트랜잭션이란
- 하나의 논리적 작업 단위로 묶여서, 전부 성공하거나 전부 실패해야 하는 DB 연산들의 묶음이다 (보충)
- 예: 주문 결제는 결제 기록 저장, 주문 상태 변경(PENDING → PAID), 재고 차감이 한 묶음이다. 하나라도 실패하면 모두 되돌려야 한다 (예시 흐름은 [[ShoppingMall - 트러블 슈팅 기록]]의 토스 결제 시퀀스)

#### ACID
- **원자성(Atomicity)**: 전부 반영되거나 전혀 반영되지 않는다
- **일관성(Consistency)**: 트랜잭션 전후로 [[무결성 제약조건]]을 만족한다
- **고립성(Isolation)**: 동시에 실행되는 트랜잭션끼리 서로 간섭하지 않는다
- **지속성(Durability)**: 커밋된 결과는 장애가 나도 남는다
- 네 속성의 이름은 [[DB(DataBase)]]에 정리돼 있고, 각 설명은 (보충)

### DBMS에서의 역할

#### 동시성 제어
- DB 시스템은 동시접근 제어로 여러 사용자가 같은 데이터를 동시에 다뤄도 일관성을 유지한다. DBMS 기능 중 "데이터 제어: 동시성 제어 및 백업"에 해당한다 — [[DB]]
- 대표 기법은 락(lock)과 격리 수준(isolation level)이다 (보충)

#### 회복
- 장애가 나도 커밋된 데이터는 살리고, 커밋되지 않은 작업은 되돌린다. 수업 노트의 "일관성 유지, 복구" 기능이다 — [[DB]]
- 변경 내용을 로그에 먼저 기록하고 장애 후 재생하는 WAL 방식이 대표적이다. Redis의 AOF도 같은 발상이다 — [[Redis]] 8번

## 실전: ShoppingMall

### 재고 차감

#### 원자성이 필요한 이유
- 결제가 성공하면 재고를 줄이는 작업은 결제 기록과 한 묶음이어야 한다. 노트에도 "수량 차감 기능을 트랜잭션으로 구현해야 함"(2026-08-12 주차), "트랜잭션을 통해 재고 처리의 원자성을 보장할 수 있어야 하는데"(2026-08-19 주차)라고 적혀 있다 — [[ShoppingMall - 트러블 슈팅 기록]]
- E2E 점검에서 @Transactional은 붙였지만 재고 처리 로직 자체가 없었다는 것을 발견했다 (2026-08-19 주차)

#### @Transactional만으로는 동시 주문을 막지 못한다
- (보충) @Transactional은 한 요청 안의 작업을 원자적으로 묶어줄 뿐이다. 두 요청이 같은 재고를 동시에 읽고 각자 차감하는 경쟁 상태(lost update)까지 막아주지는 않는다 (MySQL 기본 격리 수준 기준)
- (보충) 해결 방법은 세 가지가 대표적이다
    1. 비관적 락: `SELECT ... FOR UPDATE`로 읽는 순간 잠근다
    2. 낙관적 락: 엔티티에 `@Version`을 두고, 충돌하면 재시도한다
    3. 조건부 UPDATE: `UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?` 한 문장으로 확인과 차감을 동시에 한다
- 재고 로직을 구현할 때 이 중 하나를 고르고, 동시 주문 테스트를 함께 작성하면 좋다
