# 4. 고급

## 3. 뷰
- 하나 이상의 테이블을 합하여 만든 가상의 테이블.
⇒ SELECT문을 통해 얻은 최종 결과물을 가상 테이블로 정의하여 실제 테이블처럼 사용할 수 있도록 만든 데이터베이스 개체.
#### 장점
1. 편리성 / 재사용성: 자주 사용하는 질의를 view로 정의해 놓음. view로 또 다른 view 생성 가능.
2. 보안성: 민감한 데이터를 제외하고 view에 담아 보여줄 수 있음.
3. 독립성: 원본 테이블의 구조가 변경되어도 응용 프로그램에 영향 X.
    → 테이블을 쪼개도 조인문으로 응용 프로그램에 지장 없는 view 생성.

#### 단점
1. 원본 데이터 값에 따라 변함. → 스냅샷 불가
2. 독립적인 인덱스 생성이 어려움.
3. CUD 연산에 많은 제약
4. 뷰의 정의 변경 불가
5. 뷰에 대한 쿼리는 실제 데이터를 추출하여 만들기 때문에, 쿼리가 복잡하거나 실제 데이터 양이 많을 경우 성능 저하.

- **생성**: CREATE VIEW <view_name> AS SELECT ~
    ⇒ 이후 FROM <view_name>으로 참조
- **수정**: 정의 변경이 불가능하기에 교체 작업 ⇒ CREATE OR REPLACE VIEW <...>
- **삭제**: DROP VIEW

## 4. 인덱스
- 데이터를 쉽고 빠르게 찾을 수 있도록 만든 자료구조
### 액세스 시간
탐색 시간(액세스 헤드를 트랙에 이동시키는 시간) + 회전 지연 시간(섹터가 액세스 헤드에 접근하는 시간) + 데이터 전송 시간(데이터를 주기억장치로 읽어오는 시간)
	⇒ 액세스 속도는 주기억장치보다 100배 이상 느림 → 속도 문제.
	→ DBMS는 주기억장치의 일부를 버퍼풀로 만들어 속도 문제 해결.

### 엔진
- DBMS 내부에서 쿼리를 받아 데이터를 돌려주는 주체.
- 서버 엔진: 쿼리 요청 시, 쿼리 파싱, 스토리지 엔진에 데이터 요청 작업 수행
- 스토리지 엔진: 물리적 저장장치에서 데이터를 읽어 옴.

### 인덱스
- B-TREE 인덱스를 통해 데이터 테이블에 효과적으로 접근 가능함.
#### 장점
- 검색 속도 향상 (모든 경우는 아님)
- 쿼리 부하 ↓ (다른 요청 가능)
#### 단점
- 추가 공간 (인덱스 저장)
- 처음 생성 시 → 시간 소요
- 변경 작업이 자주 발생 시 성능 하락
#### 특징
1. 인덱스는 테이블에서 한 개 이상의 속성을 이용해 생성.
2. 빠른 검색과 효율적인 레코드 접근
3. 테이블보다 적은 인덱스 공간
4. 저장된 값들은 테이블의 부분 집합
5. B-TREE 구조
6. CUD 발생 시 인덱스 재구성
7. 열 단위 인덱스 생성
8. 데이터 중복도가 높은 열은 인덱스로 만들어도 효용 X.
9. SELECT 쿼리의 WHERE / JOIN에 인덱스 주로 사용. SELECT의 쿼리 성능 향상 목표
10. 외래키 열에는 인덱스를 되도록 생성 ⭐
11. 사용 X 인덱스 제거.

- 재구성: ANALYZE TABLE <table_name>
- 삭제: DROP INDEX <Col_name> ON <table_name>

### MySQL Index
#### 클러스터 인덱스
- 기본키를 기준으로 생성된 B-TREE 인덱스, 기본키가 없는 경우 UNIQUE 속성에 대해 생성. UNIQUE 속성도 없으면 자체 생성 ROW ID 사용.
1. 테이블당 하나만 존재.
2. 리프 노드들이 정렬된 상태로 저장된 테이블 자체가 된다.
3. 특정 값 / 범위 탐색 용이
4. CUD 느림
5. 차지 공간 적음
6. PK 생성 시 자동 생성.
#### 보조 인덱스
- PK가 아닌 컬럼을 통해 CREATE INDEX로 생성되는 인덱스. 리프에 컬럼 값 + 기본키 값. 무작위 저장.
⇒ 조건에 맞는 기본키 값을 찾고, 기본키로 클러스터 인덱스를 다시 탐색하여 값을 찾음.

1. CUD는 클러스터에 비해 빠름
2. 조회에 대해서는 클러스터가 훨씬 빠름.
⇒ 보통 위 두 인덱스를 같이 사용.
- 고려사항
	1. 인덱스는 WHERE 절에 자주 사용되는 속성이어야 한다.
	2. 인덱스는 JOIN 절에 자주 사용되는 속성이어야 한다.
	3. 인덱스가 많으면 속도 저하
	4. 속성 가공 시 사용 X
	5. 속성 선택도가 낮을 때 유리.

# 6. 데이터 모델링

## 1. 데이터 모델링의 개념

- 데이터 모델링 : 현실 세계의 복잡한 개념을 단순화 / 추상화하여 데이터베이스화하는 과정
- 정보를 모델링하고, 데이터 모델링을 거쳐, 실제 데이터베이스 구축까지를 의미함.

### 1. 데이터베이스 생명주기
- DB는 최초 사용자의 요구에 따라 구축 및 사용되다가 필요에 따라 개선 / 재구축되어 사용
- 위처럼 DB생성과 운영에 관련된 특징을 데이터베이스 생명주기라고 함.

### 2. 과정
1. 요구사항 수집 및 분석 : 현실 세계의 대상 및 사용자의 요구사항을 정리 및 분석, 데이터 베이스 구축범위 결정, 요구사항 명세서 도출
2. 설계 : 개념적 모델링 / 논리적 모델링 / 물리적 모델링
	- 개념적 모델링 : 분석된 요구사항을 기반으로 주요 개념 및 업무 프로세스를 식별하여 ERD 도출
	- 논리적 모델링 : ERD - RDB를 매핑, 정규화, 상세 속성 정의 등 DBMS종류에 적합한 변환(릴레이션 스키마 도출)
	- 물리적 모델링 : DBMS로 구현가능한 물리적 설계로 테이블 스키마(DDL) + 물리적 구조 설계 + SQL 튜닝 등이 이뤄짐
3. 구현 : 물리적 모델링을 바탕으로 DB 생성 + 서비스 제공 프로그램 제작 완성
4. 운영 : 서비스 구축 및 제공
5. 감시 및 개선 : 문제점 파악 및 개선

#### 요구사항 수집 및 분석
- 현실 세계를 파악하고, 사용자의 요구사항을 수집 및 분석하는 단계
- 실제 문서를 수집 및 분석
- 담당자와 인터뷰 및 설문조사를 통해 요구사항 직접 수렴
- 비슷한 업무를 처리하는 기존 데이터베이스를 분석한다
- 각 업무와 연관된 모든 부문을 살펴본다
→ 수집된 요구 사항에 따라 요구사항 명세서 작성

#### 개념적 모델링
- 현실 세계의 중요 데이터 추출 및 개념세계로 옮기는 작업
- 요구사항 수집 및 분석한 결과(요구사항 명세서)를 토대로 업무의 핵심 개념 구분, 전반적이 뼈대를 만드는 과정
→ 요구사항 명세서를 통해 핵심 개념을 추출하여 ERD를 출력함

#### 논리적 모델링
- 개념적 구조를 논리적 모델링하여 DB의 논리적 구조로 표현
- 위 개념적 모델링을 통해 만든 ERD를 사용하고자 하는 DBMS에 맞춰 사상(매핑)하여 실제 데이터베이스로 구현하기 위한 모델을 만드는 과정

1. 개념적 모델링에서 추출하지 않았던 상세 속성들을 모두 추출 : 핵심 속성만 추출한 개념적 모델링과 달리, 실제 필요한 모든 속성을 추출한다.
2. 정규화 수행
3. 데이터 표준화 수행 : 데이터 용어 사전과 도메인을 정의하여 동일하게 사용되는 용어 정리 및 데이터의 형태 / 크기 등을 확정

#### 물리적 모델링
- 작성된 논리적 모델을 실제 컴퓨터의 저장 장치에 저장하기 위한 물리적 구조 정의 및 구현 과정

- 응답시간 최소화
- 얼마나 많은 트랜잭션을 동시에 발생시킬 수 있는지 검토 → 트랜잭션을 효율적으로 분산시키는게 목표
- 데이터 저장 공간을 효율적으로 배치 → 데이터 특성에 따른 저장 방법을 결정하거나, 사용 형태에 따른 인덱스 설계를 통해 최적의 성능 지향

## 2. ER 모델
- 개념적 모델링에 사용되는 모델
- 개체와 속성, 관계로 데이터들을 표현함
- ER 모델은 개체와 개체 간의 관계를 ERD라는 표준화된 그림으로 표현함
- DBMS나 특정 데이터 모델과 무관하게 설계 가능

### 1. 개체와 개체 타입
- 개체 : 독립적인 의미를 지닌 유무형의 사람 또는 사물을 말함
- 개체 타입 : 개체를 구성하는 속성들로 정의한 개체의 구조 → 개체 집합의 동일한 특징을 속성으로 묶은 후, 개체에 나열
- 개체 인스턴스 : 개체를 구성하는 속성이 실제 값을 가짐으로서 실체화된 개체
- 개체 집합 : 개체 인스턴스들의 모임
⇒ 개체, 개체 타입, 개체 집합은 서로 다른 용어이지만 혼동의 소지가 없으면 개체라고 모두 줄여서 말함.

> 고객(이름, 주소, 연락처, 적립금)에서 고객은 개체 이름이고, ( ) 안에는 속성이 나열되어 있다. 이렇게 정의된 고객(이름, 주소, 연락처, 적립금)이 개체 타입이다.  
> 
> 여기에 실제 값이 들어간 (홍길동, 서울시 종로구, 010-1234-5678, 1000)이 개체 인스턴스이고, 이런 개체 인스턴스들이 모여 고객 개체 집합을 이룬다.

- 개체는 요구사항 명세서를 통해 도출되며, 일반적으로 명사가 많음. 이후 개체 집합으로 분류 및 공통된 속성을 추출하여, 의미를 가장 잘 표현할 수 있는 개체 타입을 찾음
- 개체는 반드시 데이터베이스화 되어야 함 → DB에 저장하고, 관리해야 되는 데이터들만 개체로 뽑기 때문에, 데이터베이스화는 필수임

- 특징
	- 유일한 식별자에 의해 식별 가능
	- 꾸준한 관리 필요한 데이터
	- 두 개 이상 영속적으로 존재
	- 업무 프로세스에 이용
	- 반드시 자신의 특징을 나타내는 속성 포함
	- 다른 개체와 최소 한 개 이상 관계 형성

#### 개체 타입의 ER 다이어그램 표현
- 강한 개체 타입 : 다른 개체의 도움 없이 독자적으로 존재 가능한 개체
- 약한 개체 타입 : 독자적 존재가 불가능하고, 상위 개체 타입을 가짐(의존적)

--- 강한 개체, 약한 개체 기호 그리기

- 특징
	- 강한 개체와 약한 개체는 일반적으로 1:N관계
	- 약한 개체는 강한 개체에 필수적 참여 → 약한 개체끼리의 참조도 가능하지만, 결국 의존의 최상위 층에는 강한 개체가 존재
	- 약한 개체는 강한 개체의 키를 포함하여 키를 구성함

### 2. 속성
- 개체가 가진 성질
#### 속성의 ER다이어그램 표현
- 개체에 실선으로 연결된 타원에 속성을 넣어 표기함
- PK인 경우, 속성 이름에 밑줄을 그음

#### 속성 유형
##### 의미의 분해 가능성
- 속성을 더 작은 단위(의미)로 분해할 수 있는지에 따라 구별
- 단순 속성 : 더 이상 분해 불가능한 속성
- 복합 속성 : 분해 가능한 속성

##### 속성 값의 개수
- 속성에 실제값을 넣을때, 속성값에 따라 구별
- 단일값 속성 : 값이 한 개 (일반 타원)
- 다중값 속성 : 값이 여러개 (이중 타원)

##### 기존 속성 값에서 유도 가능 여부
- 다른 속성으로부터 유도가 가능한 속성인지에 따라 구별
- 저장 속성 : 다른 속성의 영향 없이 단독으로 저장되는 속성 (사용자 생일, 전화번호 등)
- 유도 속성 : 다른 저장 속성으로부터 유도(계산)된 속성(나이 → 사용자 생일로부터 계산됨)

--- 속성의 ER 다이어그램 표현(기호) 정리

### 3. 관계와 관계 타입
- 관계 : 개체 간의 연관성을 나타낸 개념
- 관계 타입 : 개체 타입과 개체 타입 간의 연결 가능한 관계 정의
- 관계 집합 : 관계로 연결된 집합

--- 관계 ER 다이어그램 표현 정리

#### 관계 타입의 유형
##### 차수에 따른 유형
- 관계에 참여하는 개체타입의 수 기준
- 1진 관계(순환관계) : 한 개의 개체가 자기 자신과 관계를 맺는 경우
- 2진 관계 : 두 개의 개체가 관계 맺는 경우
- 3진 관계 : 세 개의 개체가 관계 맺는 경우

##### 관계 대응 수에 따른 유형
- 두 개체 타입의 관계에 실제로 참여하는 개별 개체 수를 의미
- 1:1 관계 : 좌 개체 타입과 우 개체 타입이 1대1로 대응
- 1:N 관계(N:1) : 하나의 개체 타입에 다른 쪽 여러 개체 타입과 관계를 맺는 경우
- N:M 관계 : 각 개체 타입의 개체들이 서로 임의의 개체들과 복합적인 관계

##### 관계 대응 수의 최솟값과 최댓값
- 관계 대응 수에서는 보통 최댓값을 의미 → 최솟값 표시 x
- ERD에서 최솟값을 표시하고 싶으면 (min, max)로 표시

--- ERD

#### ISA 관계
- 상위 개체 타입에 따라 하위 개체 타입이 결정되는 형태
- 슈퍼클래스 : 상위 개체 타입
- 서브클래스 : 하위 개체 타입
⇒ 상위 개체 타입에 공통 속성을 넣고, 서브 클래스에 각 개체 타입에 따른 고유 속성 부여

--- ISA 관계 ERD

#### 참여 제약 조건
- 개체 집합 내 모든 개체가 관계에 참여하는지 확인
- 전체 참여 : 개체 집합의 모든 개체가 관계 참여
- 부분 참여 : 일부만 참여

#### 역할 
- 개체 타입 간의 관계 표현 시 개체는 고유한 역할 담당. 
- 관계만으로 알 수 있으면 생략하지만, 명확하지 않는 경우 표기

#### 순환적 관계
- 동일 개체 타입 끼리의 순환적 관계

### 4. 약한 개체 타입과 식별자
- 약한 개체 타입이 존재할 경우, 약한 개체와 강한 개체 사이의 관계를 표현하는 식별 관계 타입이 요구됨
- 식별자는 약한 개체 타입에서 개별 개체를 구분하는 속성으로, 강한 개체의 키와 복합적으로 사용 가능함

--- 약한 개체 타입, 식별 관계 타입, 키, 식별자의 (기호, 의미, 설명)을 나타낸 표

### 5. IE 표기법
- 피터 첸 표기법 : 앞선 표기법처럼, 직사각형에 개체 이름을 넣고, 속성을 타원에 넣어 실선에 매핑하는 방식
- IE 표기법 : 클래스 다이어그램처럼 개체를 표기하고, 이를 관계 기호로 관계를 표현함.

--- IE 표기법 (기호, 의미)

## 3. ER 모델을 관계 데이터 모델로 사상(매핑)
- ER 모델 : 데이터베이스 생명주기의 개념적 모델링에서 사용하는 모델, ERD로 완성
- ER 모델이 실제 데이터베이스로 구축되려면 논리적 모델링 단계를 거쳐야 하고, 이때 매핑(사상)이 필요

### ER 모델(ERD) → 릴레이션 테이블

#### 개체 타입의 매핑
1. 강한(정규) 개체 타입 : 정규 개체 타입 E의 경우 대응하는 릴레이션 R 생성, 개체의 필수 속성과 추가속성들을 표시하고, PK/FK 표시
2. 약한 개체 타입 : 약한 개체 타입에서 생성된 릴레이션은 자신의 키 + 강한 개체 타입의 키를 외래키로 넣어 자신의 기본키를 구성

#### 관계 타입의 매핑
- 각 관계 타입이 맺고 있는 차수와 관계 대응 수에 따라 사상 방식 구분
	1. 차수가 3(한 관계에 연결된 개체가 셋)이상인 모든 다진 관계의 경우 관계를 하나의 릴레이션으로 표현 후, 관계에 연결된 모든 개체의 PK를 속성으로 가짐
	2. 차수가 2이고, N:M인 경우, 2번과 동일
	3. 차수가 2이고, 1:N관계는 N의 위치인 릴레이션에서 1의 위치 릴레이션의 PK를 FK로 참조
	4. 1:1 또한 외래키로 표현, 이때는 4번과 달리 방향 상관 없음

#### 다중값 속성의 매핑
- 하나의 속성이 여러 값을 가질 수 있는 속성이 존재(존재하지 않는 경우도 있음)
- 다중값이 존재 가능한 속성은 이중 타원으로 표시함.
- 릴레이션에서는 다중값을 갖는 속성을 하나의 릴레이션으로 만들고, 개체의 PK를 참조하게 만듦.

--- ERD 예시 필요

⇒ 최종적으로 개체 타입의 매핑 → 관계 타입의 매핑 → 다중값 속성의 매핑 순서로 매핑을 함.
