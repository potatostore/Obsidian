# Drawthon - MVP 시나리오

봉사 공고를 1365에서 가져오거나 직접 올리고, 회원이 공고를 보고 신청하는 서비스의 MVP 흐름이다. 각 단계의 API와 결과는 2026-11-10 백엔드 기준(커밋 전 변경 포함)으로 테스트와 실제 호출에서 확인한 동작이다. API 상세는 [[Drawthon - API 명세서]]에 있다.

## 등장인물

| 역할 | 누구 | 할 수 있는 일 |
|---|---|---|
| 비회원 | 처음 들어온 방문자 | 지도 마커 보기, 회원가입, 로그인 |
| 봉사자 (USER) | 회원가입한 사람 | 공고 조회, 신청, 철회 |
| 관리자 (ADMIN) | 서버 시작 시 환경변수로 만든 계정 | 공고 조회, 1365 등록, 직접 생성, 수정, 삭제 |

## 전체 흐름 한눈에 보기

1. 관리자가 공고를 올린다 → 1365에서 가져오기 또는 직접 작성으로 갈라진다 (시나리오 2)
2. 비회원이 들어와 지도를 보고, 회원가입 후 로그인한다 (시나리오 1)
3. 봉사자가 공고 목록과 상세를 보고 신청한다 → 성공 또는 실패로 갈라진다 (시나리오 3)
4. 봉사자가 신청을 철회하거나 다시 신청한다 (시나리오 3)
5. 관리자가 공고를 수정하거나 삭제한다 (시나리오 4)
6. 어느 단계에서든 세션 만료, CSRF 누락, 권한 없음이 생기면 예외 흐름으로 간다 (시나리오 5)

데모 순서는 2 → 1 → 3 → 4 순서가 자연스럽다. 공고가 있어야 봉사자가 볼 것이 있기 때문이다.

---

## 시나리오 0. 공통 준비

모든 화면이 처음 열릴 때와 변경 요청(POST, PUT, DELETE) 전에 거친다.

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 0-1 | 앱 접속 | GET /api/auth/csrf | CSRF 토큰과 헤더 이름(X-XSRF-TOKEN) 받음 |
| 0-2 | 로그인 상태 확인 | GET /api/auth/me | 로그인 상태면 200과 role, 아니면 401 |

0-2 결과에 따라 갈라진다.

| 분기 | 조건 | 다음 |
|---|---|---|
| 0-2-A | 401 | 비회원 화면 → 시나리오 1 |
| 0-2-B | 200, role이 USER | 봉사자 화면 → 시나리오 3 |
| 0-2-C | 200, role이 ADMIN | 관리자 화면 → 시나리오 2, 4 |

## 시나리오 1. 비회원 → 회원가입 → 로그인

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 1-1 | 지도에서 봉사 위치 둘러보기 | GET /api/map/notices | 마커 목록 (로그인 없이 가능) |
| 1-2 | 마커 클릭 | GET /api/map/notices/{noticeId} | 공고 요약 (제목, 기관, 주소, 모집 기간, 상태) |
| 1-3 | 공고 목록이나 신청을 누름 | GET /api/v1/posting | 401 → 로그인 화면으로 이동 |
| 1-4 | 회원가입 | POST /api/auth/signup | 201, role은 항상 USER. 자동 로그인되지 않음 |
| 1-5 | 로그인 | POST /api/auth/login | 200, 세션 쿠키 발급 |
| 1-6 | 내 정보 확인 | GET /api/auth/me | role USER → 시나리오 3 |

1-4 회원가입 분기

| 분기 | 조건 | 결과 | 다음 |
|---|---|---|---|
| 1-4-A | 정상 입력 | 201 | 1-5 로그인 |
| 1-4-B | 이메일 형식 오류, 비밀번호 8자 미만, 닉네임 누락 | 400 | 입력 수정 후 다시 1-4 |
| 1-4-C | 이미 가입한 이메일 | 409 | 로그인으로 안내 (1-5) |

1-5 로그인 분기

| 분기 | 조건 | 결과 | 다음 |
|---|---|---|---|
| 1-5-A | 이메일·비밀번호 일치 | 200 | 1-6 |
| 1-5-B | 불일치 또는 없는 이메일 | 401 (어느 쪽인지 구분하지 않음) | 다시 1-5 |

> [!warning] 지도 → 공고 연결 없음
> 1-1, 1-2의 지도 마커는 서버 시작 시 넣는 더미 3건(map_notices)이다. 관리자가 올린 공고(post)와 다른 테이블이고 ID도 다르다. 그래서 마커를 눌러 공고 상세나 신청으로 이어갈 수 없다.

## 시나리오 2. 관리자가 공고 올리기

시작 조건: 서버를 ADMIN_EMAIL, ADMIN_PASSWORD 환경변수와 함께 실행해 관리자 계정이 있다.

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 2-1 | 관리자 로그인 | POST /api/auth/login | 200 |
| 2-2 | 내 정보 확인 | GET /api/auth/me | role ADMIN → 관리자 화면 |
| 2-3 | 공고 등록 방식 선택 | | 아래 2-A 또는 2-B로 갈라짐 |

### 2-A. 1365 공고 가져오기

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 2-A-1 | 키워드로 1365 검색 | GET /api/v1/posting/external?keyword=&pageNo=&numOfRows= | 1365 공고 한 페이지 (저장되지 않음) |
| 2-A-2 | 다음 페이지 보기 | 같은 API, pageNo + 1 | 빈 목록이나 요청 건수보다 적으면 마지막 페이지 |
| 2-A-3 | 공고 하나를 골라 등록 | POST /api/v1/posting/external (프로그램등록번호) | 1365 상세를 가져와 저장 |

2-A-3 분기

| 분기 | 조건 | 결과 | 다음 |
|---|---|---|---|
| 2-A-3-a | 정상 | 200, 공고 저장 | 공고 목록에 노출 → 시나리오 3에서 봉사자가 봄 |
| 2-A-3-b | 이미 등록한 등록번호 | 409 | 다른 공고 선택 |
| 2-A-3-c | 1365에 없는 등록번호 | 404 | 다시 검색 |
| 2-A-3-d | 1365 호출 실패 / 인증키 미설정 | 502 / 503 | 잠시 후 재시도, 또는 2-B 직접 작성 |

### 2-B. 공고 직접 작성

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 2-B-1 | 제목, 내용, 봉사 기간, 활동 시간, 모집 기간, 모집 인원, 장소 입력 | | |
| 2-B-2 | 등록 | POST /api/v1/posting | 저장. 등록번호와 기관명은 비어 있음 |

2-B-2 분기

| 분기 | 조건 | 결과 | 다음 |
|---|---|---|---|
| 2-B-2-a | 정상 | 200 | 공고 목록에 노출 |
| 2-B-2-b | 필수값 누락, 종료일이 시작일보다 빠름, 모집 인원 0 이하 | 400 | 입력 수정 후 다시 2-B-2 |

## 시나리오 3. 봉사자가 공고 보고 신청하기

시작 조건: 봉사자로 로그인했고(시나리오 1), 공고가 하나 이상 있다(시나리오 2).

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 3-1 | 공고 목록 보기 | GET /api/v1/posting | 최신 등록순 요약 목록 |
| 3-2 | 공고 상세 보기 | GET /api/v1/posting/{postingId} | 내용, 활동 시간, 현재 신청 인원 포함 |
| 3-3 | 신청 | POST /api/v1/posting/{postingId}/application | 아래 분기 |

3-3 신청 분기

| 분기 | 조건 | 결과 | 다음 |
|---|---|---|---|
| 3-3-a | 모집 기간 안, 자리 있음, 처음 신청 | 200, 신청 인원 +1 | 3-4 철회 가능 |
| 3-3-b | 이미 신청함 | 409 이미 신청한 공고입니다. | 신청 완료 상태로 표시 |
| 3-3-c | 모집 시작 전 또는 종료 후 | 409 모집 기간이 아닙니다. | 신청 버튼 비활성화 |
| 3-3-d | 모집 인원이 다 참 | 409 모집 인원이 마감되었습니다. | 신청 버튼 비활성화 |
| 3-3-e | 공고가 그사이 삭제됨 | 404 | 목록으로 돌아감 |

- 모집 종료일 당일까지 신청할 수 있다.
- 모집 인원이 없거나 0인 공고는 인원 제한이 없다.
- 여러 명이 동시에 마지막 자리를 신청해도 모집 인원을 넘지 않는다.

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 3-4 | 신청 철회 | DELETE /api/v1/posting/{postingId}/application | 200, 신청 인원 -1. 신청 내역이 없으면 404 |
| 3-5 | 다시 신청 | POST /api/v1/posting/{postingId}/application | 철회 후에는 다시 신청 가능 (3-3으로) |
| 3-6 | 로그아웃 | POST /api/auth/logout | 204 → 비회원 화면 |

## 시나리오 4. 관리자가 공고 관리하기

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 4-1 | 공고 목록·상세에서 신청 인원 확인 | GET /api/v1/posting/{postingId} | applicantCount로 인원만 확인 가능 |
| 4-2 | 관리 방식 선택 | | 아래 4-A 또는 4-B로 갈라짐 |

### 4-A. 공고 수정

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 4-A-1 | 수정할 항목 입력 (수정 안 하는 항목도 모두 보냄) | PUT /api/v1/posting/{postingId} | 200, 수정된 공고 |

| 분기 | 조건 | 결과 |
|---|---|---|
| 4-A-1-a | 정상 | 200. 1365 원본에는 반영되지 않음 |
| 4-A-1-b | 입력 오류 | 400 |
| 4-A-1-c | 없는 공고 | 404 |

모집 인원을 현재 신청 인원보다 적게 줄여도 이미 신청한 사람은 그대로 남고, 새 신청만 막힌다.

### 4-B. 공고 삭제

| 단계 | 행동 | API | 결과 |
|---|---|---|---|
| 4-B-1 | 삭제 | DELETE /api/v1/posting/{postingId} | 200, 삭제된 공고 정보. 이 공고의 신청 내역도 함께 삭제 |

신청한 봉사자에게 따로 알림이 가지 않는다.

## 시나리오 5. 예외 흐름 (어느 단계에서든)

| 상황 | 응답 | 화면 처리 |
|---|---|---|
| 로그인 안 함, 또는 마지막 요청 후 30분 지나 세션 만료 | 401 로그인이 필요합니다. | 로그인 화면으로 → 로그인 후 하던 화면으로 |
| 변경 요청에 CSRF 토큰 없음 | 403 접근 권한 또는 CSRF 토큰을 확인해 주세요. | GET /api/auth/csrf로 토큰을 다시 받고 재시도 |
| 봉사자가 관리자 기능 호출, 관리자가 신청 호출 | 403 권한이 없습니다. | 버튼 자체를 role에 따라 숨김 |
| 로그인 중 회원 정보가 사라짐 | 401 회원 정보를 찾을 수 없습니다. 다시 로그인해 주세요. | 로그인 화면으로 |
| 1365 장애 | 502 / 503 | 관리자에게만 해당. 직접 작성(2-B)으로 우회 |

## MVP에 아직 없는 것

시나리오를 그리다 보면 필요해 보이지만 아직 API가 없는 것들이다. 데모에 필요한지 정해야 한다.

| 기능 | 영향 받는 시나리오 | 지금 상태 |
|---|---|---|
| 내 신청 내역 보기 | 3 | 없음. 봉사자는 공고 상세에서 다시 신청해 409가 나야 신청했는지 알 수 있다 |
| 공고별 신청자 명단 (관리자) | 4 | 없음. 신청 인원 숫자만 볼 수 있다 |
| 지도 마커 → 실제 공고 연결 | 1 | 없음. 지도는 더미 데이터이고 공고에는 좌표가 없다 |
| 모집 상태 표시 (모집 중, 마감) | 3 | 응답에 없다. 모집 기간과 신청 인원으로 화면에서 계산해야 한다 |
| 신청 취소·공고 삭제 알림 | 4-B | 없음 |
| 단체 신청 | 3 | 없음. 단체 인원도 각자 계정으로 신청해야 한다 |

데모에서 봉사자 흐름을 끝까지 보여 주려면 내 신청 내역이 가장 먼저 필요하고, 지도가 핵심 기능이라면 지도-공고 연결이 그다음이다.
