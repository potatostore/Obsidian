# 언리얼 기술

## 기본 방침
- 둘 다 코드 쪽 개발자 → 규칙은 C++, 블루프린트는 얇게
- 블루프린트는 바이너리 에셋이라 병합이 사실상 안 됨 → 2인 협업에서 충돌의 원인. 블루프린트는 UI 연결, 연출, 레벨 스크립트 정도만
- 데이터 주도: 유닛·몬스터·정수·아이템은 데이터 테이블(CSV/JSON 가져오기)이나 데이터 에셋으로 → 오리지널 팩과 겜바바 팩을 데이터만 바꿔 전환 ([[03 게임 개요]])
- 데이터 원본을 CSV로 두면 git에서 변경 내역이 보이고, 스프레드시트로 밸런스 작업 가능

## 구조 (안)
- 규칙 모듈: 전투 계산, CT 턴 순서, 정수 흡수 규칙을 화면과 분리된 순수 C++로 → 자동 테스트, AI 시뮬레이션, 자동 전투에 그대로 사용
- 표현 모듈: 유닛 액터, 스프라이트, 카메라, 이펙트, UI
- 검토: Gameplay Ability System(GAS). 스킬·버프·자원(영혼력) 관리에 강하지만 학습 비용이 큼 → 직접 구현과 비교 후 결정

## 렌더링·스프라이트 (결정 전)
- 스프라이트: Paper2D + PaperZD 플러그인 vs 평면 메시 + 플립북 머티리얼 직접 구현
- 카메라: 고정 구도·회전 없음으로 확정 ([[03-1 전투]]). 이전 메모는 직교 카메라. HD-2D 디오라마 느낌은 보통 원근 카메라 + 좁은 화각 + 틸트시프트 심도 → 룩 테스트로 결정 ([[Unreal Engine Main]])
- 조명: 루멘 vs 동적 라이트 + 포스트 프로세스 위주 → 성능과 룩 비교
- 그리드: 타일 데이터(높이, 지형 효과)는 규칙 모듈, 보이는 지형은 레벨 메시 → 둘을 맞추는 에디터 도구 필요

## 버전 관리
- 결정: Azure DevOps에 Git + LFS + 파일 잠금 (LFS 저장 용량 무료, 5명까지 무료, 서버 관리 불필요)
- 저장소 설정은 프로젝트 파일을 만들 때 별도 세션에서 진행
- .gitignore: Binaries, Intermediate, Saved, DerivedDataCache 제외. 공유 대상은 Config, Content, Source, Plugins, .uproject
- .uasset·.umap은 LFS로 관리하고 고치기 전에 잠금, 끝나면 바로 커밋 후 해제
- 맵은 액터별 파일 저장(One File Per Actor)으로 충돌 줄이기
- 용량 관리: 원본 작업 파일(.psd, .aseprite, .blend)은 게임 저장소 밖에 두고, Fab 에셋은 쓰는 것만 옮기기
- Perforce 전환 신호: 잠금 충돌이 잦아짐, Git이 어려운 팀원 합류, 저장소가 수백 GB가 되어 동기화가 느려짐
- 기획 문서(Obsidian) 저장소와 게임 저장소는 분리
- 지켜볼 것: Epic의 오픈소스 버전 관리 Lore (2026-06 공개, 파일 잠금은 예정 기능)

## 학습 자료
- Epic 공식 학습 포털의 무료 강좌, C++ API 문서
- 공식 샘플: Lyra(프로젝트 구조), Cropout(탑다운 전략)
- 그리드 전술 툴킷: Advanced Turn Based Tile Toolkit(Fab, 유료) → 구조 참고용
- 친구 온보딩: 유니티 ↔ 언리얼 개념 대응표 (GameObject ↔ Actor, Prefab ↔ Blueprint 클래스, ScriptableObject ↔ Data Asset)

- 그 전에는 작은 실험만: HD-2D 룩 테스트, 그리드 이동 프로토타입
